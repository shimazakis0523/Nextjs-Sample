## このSkillの位置づけ

E2E仕様書はE2E(画面を実際に操作して検証する)テストケースの元になるドキュメントであり、
ユニットテストの元にはならない。ユニットテストは詳細設計書(内部設計。コンポーネント/関数
分割)から起こすべきものであり、ユースケース記述・画面定義書は実装の内部構造を意図的に
持たないため対象外。

E2E仕様書は2つの性質が異なるセクションを持つ:

- **「仕様から導出したテストケース」**: ユースケース記述・画面定義書の記述から機械的に
  導出できるもの。このSkillが都度フル再生成する副生成物であり、手で編集してはならない。
- **「追加のテスト観点」**: 組み合わせテスト・探索的テストなど、機械的導出だけでは拾え
  ない、人の判断によるテスト観点。このSkillは絶対にこのセクションを上書き・削除しない。

## 手順

### 1. 対象画面を特定する

呼び出し時に業務ディレクトリ(例: `doc/フロントエンド設計書/業務1_Todoダッシュボード`)と
画面が指定されていればそれを使う。指定が無ければ、`doc/フロントエンド設計書/*/ユースケース記述*.md`
をGlobで列挙し、ユーザーに確認する。

### 2. ユースケース記述・画面定義書からテストケースを導出する

対象の`ユースケース記述_<画面名>.md`と`画面定義書_<画面名>.md`を読み、以下の3種類の
テストケースを導出する。導出したケースは全て、根拠となる記述(UC番号、画面入出力仕様の行
番号、処理仕様の行番号)を明記し、要件の文言自体を複製しない(リンク/参照に留める)。

**a. ユースケースに基づくケース**
各ユースケースの基本フローにつき正常系ケースを1つ、代替/例外フローにつき異常系ケースを
それぞれ1つ以上作る。

**b. 画面入出力仕様に基づくケース(項目単位)**
各項目について、以下の観点があれば個別のケースにする:
- 必須項目: 未入力で操作をブロックされることを確認するケース
- 文字数上限がある項目: 上限值ちょうど/超過の境界値ケース。「上限なし」と明記されている
  項目は境界値ケースの対象外(その旨は導出しない、無理に作らない)
- 許容値が固定選択肢(ドロップダウン等)の項目: 各選択肢を選べることを確認するケース
- プレースホルダの有無: 「なし」以外(実際にヒント文言がある)の場合のみ表示確認ケースを
  作る

**c. 処理仕様に基づくケース(分岐網羅)**
各行について、成功/失敗などの分岐があれば、分岐ごとに1ケース作る。「この操作に対する処理
は無い」という行(例: 未対応のキー操作)も、期待通り何も起きないことを確認する回帰的な
ケースとして含める。

重複除去: a/b/cの間で実質的に同じ確認内容になる場合は1ケースにまとめてよいが、その場合は
根拠欄に複数の参照元を併記する。

### 3. `E2E仕様書_<画面名>.md`を生成・更新する

対象ファイルが既に存在する場合、「仕様から導出したテストケース」セクションのみを、手順2の
結果で完全に置き換える(フル再生成)。「追加のテスト観点」セクションが存在すれば、内容を
一切変更せずそのまま残す。存在しない場合は空のプレースホルダ(「(なし)」等)を用意する。

ファイル構成:

```markdown
# E2E仕様書: <画面の業務行為名>

**画面ID**: `<画面ID>`

**作成日**: <日付>

**対象**: [ユースケース記述](./ユースケース記述_<画面名>.md)・[画面定義書](./画面定義書_<画面名>.md)
```

テストケースIDは画面ごとに`TC-001`から通し番号で振る(3セクションを通して連番)。

### 4. 結果を報告する

- 導出したテストケース数(種類別の内訳も)を報告する。
- 既存ファイルを更新した場合、「仕様から導出したテストケース」に何が追加/削除/変更された
  かを報告する。「追加のテスト観点」に変更が無いことも明示する。
- ユースケース記述・画面定義書側に、テストケース化しづらい曖昧な記述(境界条件が不明瞭等)
  を見つけた場合は、自動修正せず具体的に報告する。
