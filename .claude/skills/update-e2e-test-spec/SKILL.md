## このSkillの位置づけ

E2E仕様書はE2E(画面を実際に操作して検証する)テストケースの元になるドキュメントであり、
ユニットテストの元にはならない。ユニットテストは詳細設計書(内部設計。コンポーネント/関数
分割)から起こすべきものであり、ユースケース記述・画面定義書は実装の内部構造を意図的に
持たないため対象外。

E2E仕様書は2つの性質が異なるセクションを持つ:

- **「仕様から導出したテストケース」**: ユースケース記述・画面定義書の記述から機械的に
  導出できるもの。このSkillが都度フル再生成する副生成物であり、手で編集してはならない。
- **「追加のテスト観点」**: 組み合わせテスト・探索的テストなど、機械的導出だけでは拾え
  ない、人の判断によるテスト観点。このSkillは絶対にこのセクションを上書き・削除しない。

## 手順

### 1. 対象画面を特定する

呼び出し時に業務ディレクトリ(例: `doc/フロントエンド設計書/業務1_Todoダッシュボード`)と
画面が指定されていればそれを使う。指定が無ければ、`doc/フロントエンド設計書/*/ユースケース記述*.md`
をGlobで列挙し、ユーザーに確認する。

### 2. ユースケース記述・画面定義書からテストケースを導出する

対象の`ユースケース記述_<画面名>.md`と`画面定義書_<画面名>.md`を読み、以下の4種類の
テストケースを、それぞれ対応するブラックボックステスト技法(constitution.md
Development Workflowが明示するユースケーステスト・同値分割・境界値分析・条件/分岐テスト
(デシジョンテーブルテストを含む)・状態遷移テストの5技法)に基づいて導出する。人の判断に
よる組み合わせテスト・探索的テストはここに含めず「追加のテスト観点」に委ねる。導出した
ケースは全て、根拠となる記述(UC番号、画面入出力仕様の行番号、処理仕様の行番号)を明記し、
要件の文言自体を複製しない(リンク/参照に留める)。

**a. ユースケーステストによるケース**(技法: ユースケーステスト)
各ユースケースの基本フローにつき正常系ケースを1つ、代替/例外フローにつき異常系ケースを
それぞれ1つ以上作る。

**b. 同値分割・境界値分析によるケース(項目単位)**(技法: 同値分割・境界値分析)
各項目について、以下の観点があれば個別のケースにする:
- 必須項目(同値分割: 有効同値クラス=入力あり/無効同値クラス=空欄): 未入力で操作を
  ブロックされることを確認するケース
- 文字数の上限・下限がある項目(境界値分析): 上限がある場合は「上限文字数(有効境界)」
  「上限文字数+1(無効境界)」の2ケースを作る。下限(最小文字数)が別途明記されている
  場合も同様に「下限文字数(有効境界)」「下限文字数-1(無効境界)」の2ケースを作る。
  下限が「必須項目(1文字以上)」と実質的に同じ意味の場合は、必須項目のケースと統合して
  よい(その場合も根拠欄に両方の行番号を併記する)。「上限/下限なし」と明記されている側は
  その境界値ケースの対象外(無理に作らない)
- 許容値が固定選択肢(ドロップダウン等)の項目(同値分割: 選択肢ごとに1つの同値クラス):
  各選択肢を選べることを確認するケース
- プレースホルダの有無: 「なし」以外(実際にヒント文言がある)の場合のみ表示確認ケースを
  作る(技法に基づかない単純な表示確認であり、上記の同値分割/境界値分析とは性質が異なる)
- 上記のいずれにも該当しない項目(固定の見出し・ラベル、一覧テーブルの列がデータ通りに
  表示されること、行ごとの操作が対応する行にのみ作用することなど): 技法に基づかない
  基本表示確認として、画面入出力仕様に明記された表示内容がその通りに描画されることを
  確認するケースを作る。この基本表示確認は、画面入出力仕様がPrinciple VIにより画面上の
  全要素を1行ずつ列挙することを前提に、その行の内容を機械的にケース化するものであり、
  同値分割・境界値分析のような入力ドメインの分割は行わない

**c. 条件/分岐テストによるケース(処理仕様)**(技法: 条件網羅・分岐網羅。複数条件の組み
合わせで結果が決まる行はデシジョンテーブルテスト)
各行について、成功/失敗などの分岐があれば、分岐ごとに1ケース作る。「この操作に対する処理
は無い」という行(例: 未対応のキー操作)も、期待通り何も起きないことを確認する回帰的な
ケースとして含める。1つの行の結果が2つ以上の独立した条件の組み合わせで決まる場合(例:
「AかつBの場合のみ実行し、それ以外は何もしない」)は、単純に「成功/失敗」の2分岐として
扱わず、条件の組み合わせをデシジョンテーブルとして書き出し、真偽の組み合わせ(全網羅が
現実的でなければ、各条件が最低1回はtrue/falseになる代表的な組み合わせ)ごとに1ケース
作る。

**d. 状態遷移テストによるケース**(技法: 状態遷移テスト)
画面入出力仕様・処理仕様から、同じ要素が複数の表示状態を取り得ること(例: ボタンの
活性/非活性、保存中/保存完了/保存失敗、条件表示テキストの出し分け)が読み取れる場合、
その要素の状態と遷移(どの操作・イベントでどの状態からどの状態に移るか)を洗い出し、
以下を確認するケースを作る:
- 各状態への遷移が少なくとも1回は発生することを確認するケース(b/cのケースと実質的に
  同じ内容になる場合は統合し、根拠欄に複数の参照元を併記する)
- 遷移が許可されない操作(例: 保存処理中に再度Saveボタンを押す=二重送信)を行っても、
  状態が意図せず変わらないことを確認するケース

重複除去: a/b/c/dの間で実質的に同じ確認内容になる場合は1ケースにまとめてよいが、その場合は
根拠欄に複数の参照元を併記する。

### 3. `E2E仕様書_<画面名>.md`を生成・更新する

対象ファイルが既に存在する場合、「仕様から導出したテストケース」セクションのみを、手順2の
結果で完全に置き換える(フル再生成)。「追加のテスト観点」セクションが存在すれば、内容を
一切変更せずそのまま残す。存在しない場合は空のプレースホルダ(「(なし)」等)を用意する。

ファイル構成:

```markdown
# E2E仕様書: <画面の業務行為名>

**画面ID**: `<画面ID>`

**作成日**: <日付>

**対象**: [ユースケース記述](./ユースケース記述_<画面名>.md)・[画面定義書](./画面定義書_<画面名>.md)
```

### 4. 結果を報告する

- 導出したテストケース数(種類別の内訳も)を報告する。
- 既存ファイルを更新した場合、「仕様から導出したテストケース」に何が追加/削除/変更された
  かを報告する。「追加のテスト観点」に変更が無いことも明示する。
- ユースケース記述・画面定義書側に、テストケース化しづらい曖昧な記述(境界条件が不明瞭等)
  を見つけた場合は、自動修正せず具体的に報告する。
