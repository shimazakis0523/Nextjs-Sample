# ユニットテスト作成ガイドライン

## この資料の目的

ユニットテストのケース抽出・アサーションが実装者によってブレないよう、具体的な観点と
手順を定める。constitution.md Core Principle VII(Component Test Coverage)・
IX(Coverage Threshold Gate)が「テストが存在すること」「カバレッジが閾値を満たすこと」
を機械的に強制するのに対し、この資料は「どうやって網羅されたケースを抽出するか」を扱う
(機械的にはチェックできない領域)。

## テスト範囲

- **Reactコンポーネント**(`src/app/**/*.tsx`、Next.js特殊ファイル名を除く。
  constitution.md Principle VII参照): props/callbackという公開インターフェース単位で
  テストする。子コンポーネントはモックせず実際にレンダーして検証する。`fetch`等の
  外部依存はモックする。
- **Route Handler**(`src/app/api/**/route.ts`): `GET`/`POST`/`DELETE`等のexport関数
  単位でテストする。`src/lib/backend.ts`等の依存はモックし、ハンドラ自身のロジック
  (入力チェック・ステータスコード)を対象とする。
- **`src/lib/**`モジュール**: exportされた関数単位でテストする。

## テストケース抽出の手順(上から順に積み上げる)

### 1. 分岐カバレッジ(jestのbranches)を満たすための同値分割

`jest.config.ts`の`coverageThreshold`(Principle IX)を満たすことを目標に、条件分岐の
each側(true/false)を通すケースを同値分割の技法で抽出する。複合条件(`||`/`&&`)は、
個々のオペランドがそれぞれ独立して真偽を取るケースを作る。

例(`src/app/api/todos/route.ts`のPOSTバリデーション):

```ts
if (
  typeof title !== "string" || !title.trim() ||
  typeof dueDate !== "string" || !dueDate.trim() ||
  typeof assignee !== "string" || !assignee.trim() ||
  !VALID_STATUSES.includes(status)
) { ... }
```

→ `title`欠落、`title`空白のみ、`dueDate`欠落、`assignee`欠落、`status`欠落、`status`が
不正な値、の各ケースを個別に作る(`src/app/api/todos/route.test.ts`参照)。

### 2. 条件が独立していない場合はデシジョンテーブル

複数の条件が組み合わさって初めて結果が決まる場合(単純な`||`/`&&`のチェーンではなく、
同じ変数が複数の分岐に影響する、業務ルール上の組み合わせで結果が変わる等)、単純な
同値分割の圧縮ではケースが漏れる。条件の組み合わせを表に書き出し、各組み合わせ
(全網羅が非現実的なら、各条件が最低1回はtrue/falseになる代表的な組み合わせ)を
1ケースにする。`update-e2e-test-spec`スキルがE2E仕様書に対して行っているのと同じ
考え方をユニットレベルにも適用する。

### 3. 入力チェックに抵触するケース

このプロジェクトの入力チェックはフレームワークの注釈(Bean Validation等)ではなく素の
if文で書かれる。チェックの形ごとに、実施すべきケースを以下の通り対応させる:

| チェックの形 | 実施すべきケース |
|---|---|
| 必須チェック(文字列、`!value?.trim()`等) | 値がundefined、空文字、空白のみの3ケース |
| 文字数上限(境界値分析) | 上限文字数(有効境界)、上限文字数+1(無効境界) |
| 文字数下限(境界値分析) | 下限文字数(有効境界)、下限文字数-1(無効境界) |
| 固定選択肢(enum)チェック | 有効な選択肢は代表1つで可、不正な値を1ケース |
| 正規表現チェック | 業務仕様からマッチ/アンマッチのパターンを網羅する。既存の正規表現を流用するだけの場合は1つのNGケースで足りる |

### 4. 境界値分析(2点)

順序付けられた値(数値・日付等)については、有効範囲の境界とその外側1つずつを追加する
(上記の文字数上限/下限と同じ考え方を、文字数以外の順序付けられた値にも適用する)。

### 5. エラー推測

以下の観点を検討し、該当するものをケースに追加する(該当しなければ無理に作らない):

- **null/undefined**: 引数・レスポンス・環境変数(例: `backend.test.ts`の
  `BACKEND_API_URL`未設定)が無い場合
- **空文字・空白のみ・ゼロ**: 上記の必須チェックと重複する場合は統合してよい
- **日付境界**: 秒が"0"の日時、うるう年、存在しない日付・時刻(この画面が日付を扱う
  場合のみ)
- **特殊文字列**: 制御文字・絵文字・サロゲートペア(フリーテキスト入力がある場合)
- **二重送信・同一操作の連続実行**: ネットワーク遅延や多重クリックによる同一リクエストの
  重複実行。入力値ではなくタイミング/状態に起因するため見落としやすい
  (`TodoNewModal.test.tsx`の「失敗表示中に再度Saveをクリックする」ケース参照)
- **下位モジュールの失敗**: `fetch`等の外部呼び出しが失敗する場合、`Error`ではない値で
  reject/throwする場合(`backend-client.test.ts`参照)

### 6. 状態遷移テスト

保存中/失敗表示中のように、同じ要素が複数の表示状態を取り得るコンポーネントは、状態と
遷移(どの操作でどの状態からどの状態に移るか)を明示的に洗い出し、各状態への遷移と、
許可されない操作(処理中の二重クリック等)で状態が変わらないことを確認するケースを作る。
E2E仕様書の状態遷移テスト(ADR-0018)と同じ考え方をユニットレベルにも適用する。

## アサーションの原則

- 期待値は実装ではなく設計書(詳細設計書・ユースケース記述・画面定義書・
  `doc/API仕様書/**`)から設定する。実装を読んで期待値を作ると、実装のバグをそのまま
  テストが追認してしまう。
- Route Handlerのレスポンスは、ステータスコードとボディの両方をアサートする。
- モックした依存関数への呼び出しは、呼ばれたかどうかだけでなく、渡された引数の値も
  アサートする。

## トレーサビリティ

各テストケース(`it`/`test`の説明文)は、どの観点から導出したケースかが読み取れる書き方
をする(例: `"returns 400 without calling createTodo when title is missing"`は同値分割
由来と分かる)。技法名を機械的に書く必要はないが、レビュアーが「この技法のケースが
漏れていないか」を判断できる粒度で書く。

## レビュー・確認

- PRを出す前に`npm run test:coverage`を実行し、`jest.config.ts`の`coverageThreshold`
  (Principle IX)を満たすことを確認する。
- レビュアーは、テストケースの妥当性(設計書との整合性)とアサーションの妥当性
  (入力データとアサート句が対応しているか)の両方を確認する。
