# フロントエンド設計ガイド(熟慮事項)

**最終更新**: 2026-09-01

このドキュメントは、Future Architect社「Webフロントエンド開発ガイドライン」の
うち、画一的な合否ルールとして機械チェック(ハーネス)化することが適切でないと
判断した項目を記録する。

**ここに記載する項目はMUST/MUST NOTではなく、設計・実装時に一度立ち止まって
考えてほしい観点**である。`.github/scripts/`のcheck-*スクリプトやESLintルールの
ようにCIをブロックすることはなく、PRレビューでも違反として指摘する性質のものでは
ない。理由は項目ごとに異なるが、共通するのは「単一の正解を機械的に判定できない」
「プロジェクトの意図的な既存判断と単純比較すると誤検知になる」のいずれかである。
判断根拠の全体は`doc/common/adr/0024-web-frontend-guideline-conformance.md`を
参照。

## CSSクラス命名: kebab-case vs CSS ModulesのcamelCase

ガイドラインはCSSクラス名をkebab-caseで書くことを推奨している。一方、本プロジェクトの
CSS Modulesは一貫してcamelCase(`.stepCard`等)を採用しており、これは意図的な選択である
— `styles.stepCard`のようにJSのプロパティアクセスとしてそのまま参照でき、ケバブケースの
場合に必要な`styles["step-card"]`というブラケット記法を避けられる。

新しいCSS Moduleを追加するときは、この既存規約(camelCase)に合わせること。ガイドラインの
kebab-case推奨は、CSS Modulesを使わないプロジェクト(グローバルCSS・BEM等)を主に想定した
ものである点を踏まえて判断する。

## バリデーションメッセージの文言

ガイドラインは「具体的にする」「簡潔にする」「前向きにする」という3原則を挙げている
(例: 「エラーが発生しました」ではなく「パスワードは8文字以上にしてください」)。

これは文章表現の質の話であり、文字列パターンマッチでは「良い文言か」を判定できない
(機械チェックすると、これらの原則を満たす文言でも別の理由で弾かれる、あるいは
原則に反する文言でも通過する、という誤判定が避けられない)。新しい入力検証を実装する
際は、この3原則を意識してレビューで確認する。

## 画面間パラメータ連携の方式選択

画面表示に必要なパラメータをどう保持・受け渡すか(パスパラメータ/クエリパラメータ/
オンメモリ/Webストレージ)は、データの性質(共有したいか・URLに見せてよいか・
一時的か永続的か)によって都度判断すべき設計判断であり、単一の正解を強制するルール
ではない。新しい画面間連携を設計するときは、下表を参考に都度検討する。

| 方式 | 得意なケース |
| :--- | :--- |
| パスパラメータ | リソースの識別子(例: `/orders/{orderId}`)。直接リンクでの共有・再アクセスをしたい |
| クエリパラメータ | 検索条件・フィルタ。直接リンクでの共有・再アクセスをしたい |
| オンメモリ | URLに見せてはいけないデータ、複雑な構造化データ、一時的なデータ |
| Webストレージ | URLに見せてはいけないデータ、複雑な構造化データ、永続化したいデータ |

## 静的解析導入の運用哲学

ガイドラインの「静的解析」章は具体的なルールの一覧ではなく、「なぜ・どう導入するか」
という運用哲学(早期導入・段階的導入・チーム合意・fixable優先)を述べている。本
プロジェクトは既にESLint(`eslint-config-next` + sonarjs + testing-library) +
CIブロック(`code-quality`ジョブ)という体制を持っており、この章が推奨する内容とは
既に整合している。新しいLintルールを追加する際は、この章が挙げる注意点(チームへの
影響・fixableかどうか・段階的導入)を都度思い出すとよい、という位置づけの参考資料
である。
