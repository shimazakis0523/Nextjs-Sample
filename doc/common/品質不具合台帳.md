# 品質不具合台帳

**最終更新**: 2026-09-05

新規ハーネス・Lintルールの導入や人によるレビューが、既に実装済みのコード/文書に
実際の不具合を見つけたときに記録する台帳。「これから作る機能の設計」ではなく、
「既にあるものの何が実際に間違っていたか」を記録する点で、ADRとは目的が異なる
(ADRはその不具合を受けて追加したハーネス自体の設計判断を記録する)。

**品質不具合の定義**: この台帳が対象とするのは、(1) **プログラムバグ**(実装済み
コードが仕様通りに動作しない、または利用者に誤った結果・体験を返す)、(2)
**設計書のエラー**(仕様書・契約文書等の設計成果物そのものに誤り・欠落がある)の
いずれかに該当するものに限る。テスト未整備・Lintルール未導入・複雑度超過など、
コード自体は仕様通りに動作しているが検証・品質担保の仕組みが不足していた事象は、
品質不具合そのものではなく別の観点(必要なハーネスが揃っていたか)であり、この
台帳には記載しない。2026-09-02にこの定義を明確化し、該当しない過去のエントリ
(旧BUG-001, 002, 004, 006, 008)を台帳から除外した。2026-09-05には、この定義を
プログラムバグ/設計書のエラーの2値で必ず記録する**種別**フィールドとして
`scripts/generate-defect-log-data.mjs`が機械検証するようにした(この2値以外は
生成エラーになる)。詳細は[ADR-0025の追記](./adr/0025-defect-log.md)を参照。

各エントリは以下を記録する:

- **種別**: プログラムバグ/設計書のエラーの2値のみ(上記定義参照。この2値以外は
  `scripts/generate-defect-log-data.mjs`がエラーとして弾く)
- **発見区分**: どの経路で見つかったかの統制語彙(下記「発見区分の凡例」参照。
  自由記述の**発見契機**とは別に、集計・可視化のために機械可読な分類を持たせる)
- **発見契機**: 発見区分の詳細(自由記述)
- **原因分類**: なぜ検出されずに紛れ込んだか(下記「原因分類の凡例」参照)
- **横展開**: 同じ原因のバグが他の箇所にも無いか、コードベース全体を対象に確認
  したか。「実施」の場合は確認した範囲と結果を、「対象外」の場合はなぜ横展開の
  余地が無いと判断したかを記す。「未実施」のまま台帳に残すことはしない
  (対応完了の条件に含まれる — 下記Core Principle参照)。

`scripts/generate-defect-log-data.mjs`がこの台帳をパースし
`dashboard-data/defect-log.json`を生成、`/test-dashboard`の「品質不具合分析」
セクションで原因分類別・発見区分別の内訳と横展開実施状況を可視化する。

## 発見区分の凡例

| 区分 | 意味 |
|---|---|
| 新規ハーネス導入時 | そのクラスの問題を初めて検出できるハーネス/Lintルールを導入した、その初回実行で見つかった |
| 既存ハーネス実行中の副次的発見 | 別の目的で既存の仕組みを動かしている最中に、狙っていなかった問題が偶然見つかった |
| 人によるレビュー・指摘 | 機械的な検出ではなく、人が読んで/使ってみて気づいた |
| 既存スキルでの整合性確認 | 既に存在する確認用Skill(例: check-openapi-contract)を実行した結果として見つかった |

## 原因分類の凡例

| 分類 | 意味 |
|---|---|
| タスク定義の不備 | 実装タスクの記述が、本来含めるべき作業(テスト作成等)を要求していなかった |
| テスト技法の観点漏れ | 既存のテスト設計技法では、その分岐・パスに到達するケースが導出されていなかった |
| 品質ルール未導入 | そのクラスの問題を機械的に検出するLint/解析ルール・ハーネスがまだ存在しなかった |
| 契約ドキュメントの二重管理漏れ | 同じ内容を複数の文書に手で反映する必要があり、一方だけ更新された |
| 設定不備 | ビルド/テスト設定の不足が、特定の書き方(例: 型のみimport)では表面化せず潜伏していた |
| 用語・表記の誤り | コード上の不具合ではなく、ドキュメント上の用語・ラベルが実態と食い違っていた |
| ドキュメント構造のルール漏れ | 工程の一部に、成果物を検証する仕組み自体が存在しなかった |

## BUG-003: jest.config.tsに`@/*`パスエイリアスのmoduleNameMapperが無かった

**発見日**: 2026-08-31
**種別**: プログラムバグ
**発見区分**: 既存ハーネス実行中の副次的発見
**発見契機**: route.tsのサーバー側バリデーションにユニットテストを追加する作業中、
実行時import(`jest.mock("@/lib/backend")`)を初めて書いたときに発覚(既存テストは
全て`import type`経由だったため、型のみのimportではモジュール解決の不備が
表面化しなかった)
**原因分類**: 設定不備
**対象ファイル**: jest.config.ts
**修正内容**: `moduleNameMapper: { "^@/(.*)$": "<rootDir>/src/$1" }`を明示的に追加。
**横展開**: 対象外。設定ファイル1箇所のみが原因であり、他に同種の設定漏れが
入り込む箇所が無い。
**根拠**: [ADR-0019](./adr/0019-coverage-threshold-gate.md)

## BUG-005: OpenAPI YAML(BFF/Backend)がservers.description欠落・tags未定義等の複数箇所で規約に不適合だった

**発見日**: 2026-08-31
**種別**: 設計書のエラー
**発見区分**: 新規ハーネス導入時
**発見契機**: Spectralルールセット(Future Architect社OpenAPI規約準拠)導入時の
実行結果
**原因分類**: 品質ルール未導入
**対象ファイル**: doc/API仕様書/BFF/openapi.yaml, doc/API仕様書/Backend/openapi.yaml
**修正内容**: servers.description追加、tags未定義・各operationのtags/description
欠落を解消、BFFの400レスポンスをcomponents化。
**横展開**: 実施。BFF・Backend両ファイルを同一の17ルールで機械的に検査し、
両ファイルの不適合をまとめて修正した。
**根拠**: [ADR-0022](./adr/0022-openapi-style-guide-conformance.md)

## BUG-007: TodoList.tsx・mockup/page.tsxの操作列ヘッダーがaxe-coreのempty-table-header違反だった

**発見日**: 2026-09-01
**種別**: プログラムバグ
**発見区分**: 新規ハーネス導入時
**発見契機**: `jest-axe`導入時の実行結果(Automated Accessibility Test Coverage
ハーネス新設に伴う)
**原因分類**: 品質ルール未導入
**対象ファイル**: src/app/dashboard/TodoList.tsx, src/app/mockup/page.tsx
**修正内容**: `aria-label`のみだった空の`<th>`を、視覚的には隠しつつスクリーン
リーダーには読み上げられる`<span>`(`.visuallyHidden`)に置き換えた。
**横展開**: 実施。`TodoList.tsx`で最初に検出した後、同一パターン
(`<th aria-label="操作"></th>`)が`mockup/page.tsx`にも存在することを確認し、
同時に修正した。
**根拠**: [ADR-0024](./adr/0024-web-frontend-guideline-conformance.md)

## BUG-009: doc/API仕様書/Backend/openapi.yamlにPUT /todos/{id}の定義が漏れていた

**発見日**: 2026-09-01
**種別**: 設計書のエラー
**発見区分**: 既存スキルでの整合性確認
**発見契機**: `check-openapi-contract`スキルによる整合性確認(Todo編集機能の実装完了
確認として実行)。BFF契約には`PUT /todos/{id}`を追加していたが、`backend.ts`の
実バックエンド分岐が呼ぶBackend契約側への反映が漏れていた。
**原因分類**: 契約ドキュメントの二重管理漏れ
**対象ファイル**: doc/API仕様書/Backend/openapi.yaml
**修正内容**: BFF契約と対応する`put`操作(`operationId: updateTodo`)を追加。
**横展開**: 実施。`check-openapi-contract`スキルはBFF・Backend双方の全エンドポイント
を突き合わせるため、他に同種の片方だけの更新漏れが無いことを確認済み。
**根拠**: Todo編集機能実装(コミット a256962、Issue #38)

## BUG-010: test-dashboard.ymlのpaths-ignoreが広すぎ、business-map.json単独の変更を見逃す

**発見日**: 2026-09-01
**種別**: プログラムバグ
**発見区分**: 既存ハーネス実行中の副次的発見
**発見契機**: この品質不具合台帳自体の追加作業で、`defect-log.json`もコミット対象に
含めるため`.github/workflows/test-dashboard.yml`のpaths-ignoreを見直していて発覚。
`dashboard-data/**`という指定は生成物(`summary.json`)だけでなく手動保守ファイル
(`business-map.json`)も含んでしまい、`business-map.json`だけを変更するpush
(他に変更ファイルが無い場合)ではワークフロー自体が起動しない。過去3回の変更は
いずれも他のファイルと同時だったため一度も表面化していなかった(git logで確認)。
**原因分類**: 設定不備
**対象ファイル**: .github/workflows/test-dashboard.yml
**修正内容**: paths-ignoreを`dashboard-data/**`から、生成物である
`dashboard-data/summary.json`・`dashboard-data/defect-log.json`のみに限定した。
**横展開**: 実施。他のワークフロー(`spec-consistency.yml`)にpaths-ignore/paths
指定が無いことを確認し、同種の問題が他に無いことを確認した。
**根拠**: 品質不具合台帳の新設作業(このADR、[ADR-0025](./adr/0025-defect-log.md))
