# ADR-0004: 画面を持つ機能はモックアップ合意から始める

## ステータス

Accepted (2026-08-30)

## コンテキスト

これまでの要件定義プロセスは、自然言語の機能説明 → `/speckit-specify`によるspec.md生成、
という流れだった。しかし自然言語だけで画面のビジュアルデザインや外形的な機能性を伝達すると、
文章の解釈にぶれが生じやすい。モックアップ(視覚的な画面イメージ)を先に作り、それに対して
合意を得てからspec.mdに落とし込む方が、認識の齟齬を防げる。

### 検討した論点

1. **モックアップ作成を必須にするか推奨に留めるか**: 必須にするとプロセスの柔軟性が下がるが、
   このプロジェクトでこれまで繰り返し確認してきた通り、強制力の無いルールは実質守られない
   ことが多い(constitution.mdの他の`MUST`ルール群と同じ判断基準)。画面を持つ機能は認識齟齬の
   リスクが実際に高いため、必須とする。
2. **合意済みモックアップへの参照をspec.mdに残すか**: Principle VIはこれまで、
   親機能・ステータス・起動元など、spec.mdに外部参照や自己言及的なメタ情報を含めることを
   一貫して排除してきた。モックアップ参照はこの原則と一見矛盾するように見える。
   - 判別の軸は「spec.mdがその参照先に対して現在も同期していなければならないか
     (=openapi.yamlのように参照先を信頼できる一次情報源として扱うか)」。
   - モックアップは執筆時点の視覚的合意のスナップショットに過ぎず、spec.md自身が
     画面入出力仕様・処理仕様として自己完結した内容を持つ(そちらが常に正)。したがって
     openapi.yaml参照とは異なる性質の「provenance(来歴)」情報として扱えば、
     「文書のワークフロー状態」や「起動元」のような真に排除すべきメタ情報とは別物になる。

## 決定

1. 画面を持つ新機能は、`design`skillで作成したモックアップ(Artifact)の合意を得てから
   `/speckit-specify`を実行する。`speckit-specify`skillの冒頭に、モックアップの有無を
   確認する手順(step 0)を追加し、無ければ`design`skillでの作成を促していったん停止する。
   画面を持たない機能(純粋なバックエンド内部変更など)には適用しない。
2. 合意したモックアップのArtifact URLは、spec.mdのヘッダーに`**モックアップ**`フィールドとして
   残す。ただし以下を明確に区別する:
   - `openapi.yaml`参照(処理仕様内): 参照先が常に現在の契約と一致していなければならない
     一次情報源。spec.mdはその詳細を書かず参照に委ねる。
   - `モックアップ`参照(ヘッダー): 執筆時点の視覚的合意の記録。画面入出力仕様・処理仕様は
     必ず自己完結して書き、「詳細はモックアップ参照」で済ませることは禁止。spec.mdと
     モックアップが食い違った場合は常にspec.mdが正であり、モックアップを追随更新する
     義務は無い。

## 影響

- `speckit-specify`は、画面を持つ機能の説明を受け取った際、合意済みモックアップが会話内に
  存在しない限り、spec.md生成に進まず停止するようになる。
- spec-template.mdのヘッダーに`**モックアップ**`行が追加される(モックアップが無い機能では
  行ごと省略)。
- この「必須化」自体はこのセッション以前と同様、`speckit-specify`skillに書かれた手順として
  実装されているに過ぎず、CIやgit hookのような外部強制ではない。`speckit-specify`を経由せず
  直接spec.mdを書く/編集するフローには適用されない(これまで議論してきたhard gate/soft gateの
  区別と同じ限界を持つ)。

## 追記(2026-08-31): 公開が必要なモックアップは`/mockup`にも静的公開する

既存2画面(Todo一覧・Todo新規登録)のモックアップをdesignスキルでClaude Design Artifactとして
作成しトップページから公開リンクしたところ、Artifactの共有設定(既定は非公開・所有者のみ)が
原因でリンク先がサインイン画面になってしまい、GitHubリポジトリ同様に誰でも見られることを
期待するこのプロジェクトの公開デモという目的を果たせなかった。

このプロジェクトは既にGitHub・(想定される)Vercel上で公開されたアプリであり、Claude Design
Artifactの認証・共有設定に依存せずとも、モックアップ自体をアプリ内の静的ページとして公開
できる。そこで、**公開デモとして誰でも見られる必要があるモックアップ**は、
`src/app/mockup/page.tsx`に実装(対象画面の本物のCSS Module ―
`src/app/dashboard/dashboard.module.css` ― をそのまま流用した非対話的な静的レプリカ。
`fetch`や状態を持たず、ボタン・入力はすべて無効化する)し、`**モックアップ**`フィールドは
Artifact URLではなくこのアプリ内パス(`/mockup#<画面ID>-heading`)を指すよう改める。

`design`skillでのモックアップ作成(`speckit-specify`step 0、合意の場としての一時的な
Artifact)自体は変更しない。会話内で開発者と合意を取る用途には引き続き適したツールである。
変わるのは「合意後、その記録をどこに永続化するか」で、外部に公開する必要が無ければ従来通り
Artifact URLのままでよく、このプロジェクトのように公開デモとして誰でも見られる必要がある
場合にのみ、`/mockup`のようなアプリ内静的ページを追加で用意しそちらを参照先にする。

## 追記(2026-09-01): モックアップ作成そのものにGitHub Issueを切る

Todo編集機能のモックアップ作成を進めていた際、ユーザーから「イシュー切ってるか?」
「モックアップを作るというイシューを切るべきでルールに明文化」という指摘があった。

現状のパイプライン(モックアップ合意→`/speckit-specify`→`/speckit-plan`→
`/speckit-tasks`→`/speckit-taskstoissues`→`/speckit-implement`)では、GitHub Issueは
`/speckit-taskstoissues`の段階、すなわち仕様書・詳細設計書・tasks.mdが確定した
かなり後になってから作られる。モックアップ作成という、画面を持つ機能の最初の
アウトプットには、追跡用のIssueが1つも存在しない期間が生じていた。

### 決定

画面を持つ新機能でモックアップを作成する際は、モックアップ作成の**前または同時に**
GitHub Issueを作成しなければならない(`/speckit-taskstoissues`まで先送りしない)。
以降のパイプライン(仕様書・詳細設計書・tasks.md・実装)は、このIssueを起点として
進める。Issue番号は、モックアップを追加するコミット/PRのメッセージまたはPR本文で
参照する — ユースケース記述のヘッダーには含めない(Principle VIが、ヘッダーへの
プロジェクト管理メタ情報の混入を`**モックアップ**`フィールドのみを例外として
明示的に禁止しているため。Issue番号もこの意味で「文書のワークフロー状態」に該当し、
モックアップURLとは性質が異なる)。

この必須化は、ADR-0004本文が既に述べる「モックアップ必須化」自体の限界と同じく、
`speckit-specify`skillのstep 0に書かれた手順として実装されるソフトゲートであり、
CIやgit hookのような外部強制ではない。

## 影響

- `.claude/skills/speckit-specify/SKILL.md`のstep 0に、モックアップ作成前の
  GitHub Issue確認・作成手順を追加。
- `.specify/memory/constitution.md`のDevelopment Workflow節(モックアップ必須化の
  項)にこの要件を追記(v2.20.0)。
