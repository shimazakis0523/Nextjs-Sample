# ADR-0001: タスク管理のGitHub Issue粒度

## ステータス

Accepted (2026-08-30)

## コンテキスト

`tasks.md`のタスクをGitHub Issueに変換し、成果物の進捗管理をClaudeセッションの記憶ではなく
GitHub上の客観的な状態に基づかせることにした。その際、Issueをどの粒度で切るかを決める必要が
あった。

### 検討した選択肢

1. **タスク粒度(1タスク=1 Issue)**
   `speckit-taskstoissues`スキルの既定動作。T001〜T020をそれぞれ独立したIssueとして作成した
   (Issue #2〜#21)。
   - 利点: 個別タスクへのPR紐付け(`Closes #N`)、担当者アサイン、タスク単位でのコメントによる
     議論ができる。
   - 欠点: 機能全体としてどこまで進んだかを把握するには、複数のIssueを横断して見る必要がある。

2. **機能粒度・チェックリスト型(1機能=1 Issue、本文にMarkdownチェックリスト)**
   `001-todo-dashboard`という1つのIssueを立て、本文に`- [ ] T001 ...`という形でタスクを列挙する。
   - 利点: Issue1件を見れば、GitHubが自動描画する進捗バーで全体の完了率が一目でわかる。
   - 欠点: チェックリストの各項目は独立したIssueではないため、個別タスクへのPR紐付け・担当者
     アサイン・タスク単位のコメント議論ができない。

3. **機能粒度の親Issue + タスク粒度のsub-issue(GitHub Issues純正のsub-issue機能)**
   機能単位の親Issueを1件作成し、タスク単位のIssue(選択肢1で作成済みのもの)をその
   sub-issueとして紐付ける。
   - 利点: 親Issueを見れば進捗バーとsub-issue一覧で全体状況を把握できる(選択肢2の利点)。
     かつ各タスクは独立したIssueのままなので、PR紐付け・担当者アサイン・議論が可能
     (選択肢1の利点)。
   - 欠点: 親Issueの作成と、既存タスクIssueの紐付けという追加の移行作業が必要。

## 決定

選択肢3(機能粒度の親Issue + タスク粒度のsub-issue)を採用する。

`001-todo-dashboard`機能の親Issueを新規作成し、既存のT001〜T020(Issue #2〜#21)をsub-issue
として紐付ける。今後の機能追加でも、機能ごとに親Issueを1件作成し、`speckit-taskstoissues`で
生成したタスクIssueをsub-issueとして紐付ける運用とする。

## 影響

- 機能の進捗はGitHubのsub-issue進捗バーで客観的に把握できるようになる。これは
  「Claudeセッションの記憶に依存しない制御」という本来の目的に合致する。
- `speckit-taskstoissues`スキルの標準動作(タスク→Issue変換)はそのまま使えるが、変換後に
  親Issueへ紐付ける追加手順が必要になる。この手順は現時点でスキル化されていないため、
  当面は都度手動(またはClaudeへの依頼)で行う。将来的にこの手順が定型化するようであれば、
  `speckit-taskstoissues`を拡張するか、専用スキルを作ることを検討する。
