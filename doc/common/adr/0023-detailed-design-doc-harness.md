# ADR-0023: 「ハーネス」表記の是正と、詳細設計書(PD)の構造チェックハーネス新設

## ステータス

Accepted (2026-08-31)

## コンテキスト

ユーザーから、トップページの「開発プロセスとハーネス」の各カードを見て、
「ハーネスをAIが作成した成果物をチェックしてブロックする役目だと思っているが、
UIモックアップ合意・仕様書作成(BD)・実装のカードでは、成果物を作る側のスキル名
(`design skill`・`/speckit-specify`・`/speckit-implement`)がハーネスとして
書かれているように見える。理解が誤っていないか」という指摘があった。

確認した結果、ユーザーの理解が正しい。このプロジェクトが`constitution.md`の
Core Principle群(VII〜XII)・各ADRを通じて一貫して「ハーネス」と呼んできたのは、
ESLint品質ルール・Jestカバレッジ閾値・Spectral・`check-*`系スクリプトのような、
成果物を検証しCIをブロックする機構であり、成果物を生成するSkillそのものではない。
トップページの表記がこの用語法からズレていた。

修正のため各ステップの「本当のハーネス」を洗い出したところ:

| ステップ | 修正前(誤り) | 実際のハーネス |
|---|---|---|
| UIモックアップ合意 | `design skill` | `/speckit-specify`step 0の合意確認(未合意なら停止。ADR-0004) |
| 仕様書作成(BD) | `/speckit-specify` | `check-spec-sync.sh`(`spec-sync`ジョブ。E2E仕様書/画面遷移図の追従を強制) |
| 詳細設計(PD) | `/speckit-plan`・`/speckit-tasks` | **存在しなかった** |
| 実装 | `/speckit-implement` | `check-component-tests.sh`(`component-test-coverage`ジョブ) |
| 静的解析/UT/E2E/品質分析 | (修正不要) | 元から実際のゲートを指していた |

詳細設計(PD)だけ、成果物(詳細設計書.md)を検証してブロックする機構が1つも
無いことが判明した。他の全ステップに実在のゲートがある中で、この段階だけが
「作って終わり」になっていた。

### 「概要」セクションを巡る発見

詳細設計書.mdの構造チェックハーネスを設計する過程で、`constitution.md`の
Development Workflow節が「詳細設計書はセクションが厳密に2つ(登場する
コンポーネントと関係・Project Structure)」と定めている一方、実際に存在する唯一の
詳細設計書(`doc/フロントエンド設計書/業務1_Todoダッシュボード/詳細設計書.md`)には
3つ目の「概要」セクション(業務の説明+画面ID・画面名・URL・ユースケース記述/
画面定義書へのリンクを並べた一覧表)があることが分かった。

この「概要」は、ADR-0008/0010が排除対象とした`Summary`/`Technical Context`等の
spec-kitテンプレート由来の重複コンテンツ(constitution.mdの再掲や他セクションとの
重複)とは性質が異なる。画面一覧表は「登場するコンポーネントと関係」(ファイル間の
関係)にも「Project Structure」(パス一覧)にも書く場所が無い、複数画面を持つ業務
特有の必要情報であり、実質的にルールの側が抜けていた(ドキュメントの違反ではない)。

ユーザーに、この場合に「概要を正式に許可するようルールを直す」か「概要を削除して
実態をルールに合わせる」かを確認したところ、前者(ルール側を直す)を選んだ。

## 決定

### 1. トップページ・doc/common/開発サイクル図.mdの表記修正

各ステップのハーネス表記を、上表の「実際のハーネス」に修正する。

### 2. constitution.mdの詳細設計書セクション構成ルールを修正

「概要」を、複数画面を持つ業務では必須・単一画面の業務では省略可能な、任意の
第3セクションとして正式に許可する(先頭に置く)。既存の詳細設計書.mdは変更不要。

### 3. 詳細設計書の構造チェックハーネスを新設

`.github/scripts/check-detailed-design-doc.mjs`を新規作成し、
`doc/フロントエンド設計書/**/詳細設計書.md`を(PRでの変更有無によらず全件。
`openapi-routes`ジョブと同じモデル)検証する:

1. **セクション構成**: `["登場するコンポーネントと関係", "Project Structure"]`
   または`["概要", "登場するコンポーネントと関係", "Project Structure"]`の
   いずれかに完全一致すること(順序・過不足も含む)。廃止済みセクション名
   (`Summary`等)を検出した場合は専用のエラーメッセージを出す。
2. **図ファースト**: 「登場するコンポーネントと関係」の内容が空・省略記載でない
   限り、mermaid図がファイルごとの`### `サブセクションより前にあること。
3. **役割記述**: 各`### `サブセクションが、見出し直後の非空行として役割の説明を
   持つこと(見出しだけで終わらない)。

`.github/workflows/spec-consistency.yml`に`detailed-design-doc`ジョブを追加し、
PRごとに実行・違反0件を必須とする。

**意図的に対象外とした観点**:

- 「概要」の画面一覧表が実際のユースケース記述_*.mdと過不足なく対応しているか
- 「登場するコンポーネントと関係」の図が実際のprops/callback/fetch関係と一致するか
- props/callbackのエッジラベルが型シグネチャを含んでいるか(constitution.md本文が
  要求する内容だが、自由形式のMermaid記法・自然文の意味検証が必要で、単純な
  テキスト処理では高い誤検知率になる)

これらは人のレビューに委ねる。

### サンドボックス検証

実在する`doc/フロントエンド設計書/業務1_Todoダッシュボード/詳細設計書.md`が
違反0件でパスすることを確認した上で、一時ディレクトリに以下を意図的に含む
偽の詳細設計書.mdを作成し、全て検出されることを確認した:

- 廃止済みセクション名(`Summary`)の混入
- mermaid図がファイルサブセクションより後にある(図ファースト違反)
- サブセクションの見出し直後に本文が無い(役割記述欠落)

さらに、mermaid図がサブセクションより前にある正しい構成、および「概要」を含む
3セクション構成がそれぞれ違反0件でパスすることも確認した。

## 影響

- `src/app/page.tsx`のPROCESS_STEPS・`doc/common/開発サイクル図.md`の
  ハーネス表記を修正(生成スキル名 → 実際のゲート)。
- `constitution.md`に Core Principle XIII
  (Detailed Design Document Structural Conformance)を追加、Development
  Workflow節の詳細設計書セクション構成ルールを「概要」許可に修正(v2.18.0)。
- `.github/scripts/check-detailed-design-doc.mjs`を新規作成。
- `.github/workflows/spec-consistency.yml`に`detailed-design-doc`ジョブを追加。
