# 詳細設計書: Todoダッシュボード

**業務ディレクトリ**: `業務1_Todoダッシュボード`(実装ブランチ由来の識別子: `001-todo-dashboard`)

**作成日**: 2026-08-29 | **最終更新**: 2026-09-01

## 概要

ログイン不要で誰でも使える、Todoの一覧表示・新規登録・編集・削除ができる業務。この業務は
以下の3つの画面で構成される。各画面のユースケース・画面定義(画面入出力仕様・処理仕様)は、
それぞれのユースケース記述・画面定義書を参照すること。

| 画面ID | 画面名 | URL | ユースケース記述 | 画面定義書 |
|---|---|---|---|---|
| `todo-list` | Todo一覧 | `/dashboard` | [ユースケース記述(Todo一覧)](./ユースケース記述_Todo一覧.md) | [画面定義書(Todo一覧)](./画面定義書_Todo一覧.md) |
| `todo-new` | Todo新規登録 | なし(モーダル) | [ユースケース記述(Todo新規登録)](./ユースケース記述_Todo新規登録.md) | [画面定義書(Todo新規登録)](./画面定義書_Todo新規登録.md) |
| `todo-edit` | Todo編集 | なし(モーダル) | [ユースケース記述(Todo編集)](./ユースケース記述_Todo編集.md) | [画面定義書(Todo編集)](./画面定義書_Todo編集.md) |

## 登場するコンポーネントと関係

```mermaid
flowchart TD
    page["page.tsx<br/>(Server Component)"]
    dashboard["TodoDashboard.tsx<br/>(親・todos一覧stateを保持)"]
    list["TodoList.tsx<br/>(todo-list画面)"]
    modal["TodoNewModal.tsx<br/>(todo-new画面)"]
    editModal["TodoEditModal.tsx<br/>(todo-edit画面)"]
    postRoute["route.ts<br/>(BFF: GET/POST /api/todos)"]
    idRoute["[id]/route.ts<br/>(BFF: DELETE/PUT /api/todos/{id})"]

    page -- "props: initialTodos: Todo[]" --> dashboard
    dashboard -- "props: todos: Todo[], onDeleted: (id: string) => void, onEditClick: (todo: Todo) => void, onAddClick: () => void" --> list
    dashboard -- "props: onSaved: (todo: Todo) => void, onCancel: () => void" --> modal
    dashboard -- "props: todo: Todo, onUpdated: (todo: Todo) => void, onCancel: () => void" --> editModal
    list -. "callback: onDeleted(id: string) => void" .-> dashboard
    list -. "callback: onEditClick(todo: Todo) => void" .-> dashboard
    modal -. "callback: onSaved(todo: Todo) => void" .-> dashboard
    editModal -. "callback: onUpdated(todo: Todo) => void" .-> dashboard
    list -- "fetch: DELETE /api/todos/{id}" --> idRoute
    modal -- "fetch: POST /api/todos" --> postRoute
    editModal -- "fetch: PUT /api/todos/{id}" --> idRoute
```

(データそのものの書き換えは常に親`TodoDashboard.tsx`側で行う。BFFより先
(`src/lib/backend.ts`・`mock-todos.ts`)は下記Project Structureを参照。上記の
`Todo`型は[doc/API仕様書/common/schemas/Todo.yaml](../../API仕様書/common/schemas/Todo.yaml)
で定義済みのエンティティ(id/title/dueDate/assignee/status)をそのまま指し、ここでの
再列挙はしない)

### `page.tsx`

役割: 画面のエントリ(Server Component)。

`src/lib/backend.ts`の`getTodos()`(swap pointという既存ファイルに、この業務で追加する
関数。下記Project Structure参照)を呼んで初期データを取得し、`TodoDashboard`に
`initialTodos`として渡すだけ。自身は状態を持たない。

### `TodoDashboard.tsx`

役割: 親。`todos`一覧stateと各モーダルの開閉stateを持つ。

[todo-list](./ユースケース記述_Todo一覧.md)・[todo-new](./ユースケース記述_Todo新規登録.md)・
[todo-edit](./ユースケース記述_Todo編集.md)のいずれも同じ一覧データに影響する(削除で減り、
登録で増え、編集で内容が変わる)ため、どの画面にも属させず、この親が保持する。`TodoList`
から`onDeleted(id)`を受けたら`todos`からその1件を除き、`TodoNewModal`から`onSaved(todo)`
を受けたら`todos`に追加する。`TodoList`から`onEditClick(todo)`を受けたら、編集対象として
`editingTodo`(型`Todo | null`)stateにその値を保持して`TodoEditModal`を開き、
`TodoEditModal`から`onUpdated(todo)`を受けたら`todos`内の同じ`id`の要素をその内容で
置き換え、`editingTodo`を`null`に戻して閉じる。

### `TodoList.tsx`

役割: [todo-list](./ユースケース記述_Todo一覧.md)画面の実装。一覧描画と編集・削除ボタンの
処理を担当。

`todos`を描画するだけ(データ取得はこの画面の責務ではない)。行ごとの編集ボタンは自身では
何も呼び出さず、クリックされた行の`Todo`を引数に`onEditClick(todo)`で親に伝えるだけ
(編集処理・モーダル表示は親が持つ)。削除は自身が`DELETE /api/todos/{id}`を呼び、成功
したら`onDeleted(id)`で親に伝える。`todos`配列そのものの書き換えは行わない。

### `TodoNewModal.tsx`

役割: [todo-new](./ユースケース記述_Todo新規登録.md)画面の実装。新規登録フォームを担当。

入力内容・バリデーション・保存中の表示・失敗メッセージはすべて自身が持つ。Saveボタン
押下時、`POST /api/todos`を呼ぶのも自身。保存成功後、一覧への追加は行わず
`onSaved(todo)`で親に通知するだけ。表示/非表示は親が持つ`isModalOpen`stateで制御される
(自身は開閉stateを持たない)。

### `TodoEditModal.tsx`

役割: [todo-edit](./ユースケース記述_Todo編集.md)画面の実装。既存Todoの編集フォームを担当。

`todo`(編集対象)をpropsで受け取り、`Todo名`・`期限`・`担当者`・`ステータス`の入力欄の
初期値として使う点以外は`TodoNewModal.tsx`と同じ構造(入力内容・バリデーション・更新中の
表示・失敗メッセージは自身が持つ)。更新ボタン押下時、`PUT /api/todos/${todo.id}`を呼ぶ
のも自身。更新成功後、一覧の更新は行わず`onUpdated(todo)`で親に通知するだけ。表示/非表示
は親が持つ`editingTodo`stateで制御される(自身は開閉stateを持たない)。

### `route.ts` (`src/app/api/todos/route.ts`)

役割: BFFのRoute Handler。`GET /api/todos`・`POST /api/todos`を実装。

`GET`は`src/lib/backend.ts`の`getTodos()`をそのまま呼んで結果を返す。`POST`は
`title`・`dueDate`・`assignee`・`status`の必須項目チェックを行い(未入力または不正な
`status`なら400を返す)、通過したら`createTodo()`に渡し、作成されたTodoを返す(201)。
クライアント側の`TodoNewModal.tsx`も同じ必須項目チェックを行うが、これはUXのための
先行チェックであり、`route.ts`側の検証を代替するものではない。リクエスト/レスポンスの
詳細は[doc/API仕様書/BFF/openapi.yaml](../../API仕様書/BFF/openapi.yaml)を参照。

### `[id]/route.ts` (`src/app/api/todos/[id]/route.ts`)

役割: BFFのRoute Handler。`DELETE /api/todos/{id}`・`PUT /api/todos/{id}`を実装。

`DELETE`は`src/lib/backend.ts`の`deleteTodo(id)`を呼ぶだけ。`PUT`は`POST /api/todos`と
同じ必須項目チェックを行い(未入力または不正な`status`なら400を返す)、通過したら
`updateTodo(id, ...)`に渡し、更新後のTodoを返す(200)。対象idが存在しない場合は404を
返す。クライアント側の`TodoEditModal.tsx`も同じ必須項目チェックを行うが、これはUXのため
の先行チェックであり、`route.ts`側の検証を代替するものではない。レスポンスコードの詳細は
[doc/API仕様書/BFF/openapi.yaml](../../API仕様書/BFF/openapi.yaml)を参照。

## Project Structure

### Source Code (この業務が追加/変更するパス)

`backend.ts`がswap pointという1ファイルに集約される構成自体、および`mock-<entity>.ts`と
いう命名規則は[AP方式設計書(バックエンド編)](../../common/AP方式設計書(バックエンド編).md)
に記載の共通パターンであり、ここでは繰り返さない。ただし`backend.ts`内の個別の関数や
個別の`mock-*.ts`ファイルは共通インフラではなく、それを導入した業務自身の成果物である
ため、以下に明記する(AP方式設計書(バックエンド編)の「注意」参照)。

```text

│   ├── page.tsx              # Todo一覧画面のエントリ

│   ├── TodoDashboard.test.tsx
```

**Structure Decision**: Next.js App Router単一プロジェクト内にfrontendとBFFが同居する構成
([AP方式設計書(フロントエンド編)](../../common/AP方式設計書(フロントエンド編).md)参照)。
画面ごとのコンポーネント(`TodoList.tsx`・`TodoNewModal.tsx`)は、共有state(`todos`一覧・
モーダル開閉)を持つ親(`TodoDashboard.tsx`)の子として実装する(上図参照)。コンポーネント
テストのカバレッジ要件はconstitution.md Core Principle VIIを参照。
